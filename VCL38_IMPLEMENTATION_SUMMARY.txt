KEY FEATURES
================================================================================

1. WATCHLIST MANAGEMENT
   - Create watchlists with optional rules
   - Retrieve single or all user watchlists
   - Update watchlist metadata and rules
   - Delete watchlists (cascades to rules and alerts)
   - User ownership validation on all operations

2. RULE SYSTEM
   Rule Types:
   - NEIGHBORHOOD: Substring match in signal neighborhood (case-insensitive)
   - ADDRESS: Substring match in addresses list (case-insensitive)
   - ZONING: Substring match in zoning_from or zoning_to (case-insensitive)
   - SIGNAL_TYPE: Exact match of signal type (case-insensitive)
   - KEYWORD: Substring match in headline or summary (case-insensitive)
   - SEVERITY: Exact match of severity level (case-insensitive)
   
   Matching Logic:
   - Multiple rules use OR logic: matches if ANY rule matches
   - Empty rules match all signals
   - All matching is case-insensitive

3. SIGNAL EVALUATION
   - Automatic alert generation when signal matches watchlist rules
   - Prevents duplicate alerts for same signal+watchlist pair
   - Checks all active watchlists for matches
   - Returns list of created alert IDs

4. ALERT MANAGEMENT
   - Create alerts manually or automatically
   - Mark individual alerts as read
   - Mark all alerts as read in one operation
   - Filter alerts by read status
   - Support pagination with limit/offset
   - Get alert count summary (total and unread)

5. SECURITY
   - JWT authentication required for all endpoints
   - User ownership validation
   - Parameterized SQL queries prevent injection
   - Pydantic input validation
   - Proper HTTP status codes
   - Comprehensive error handling

6. PERFORMANCE OPTIMIZATION
   - Strategic indexes on user_id, watchlist_id, is_read, created_at
   - Unique constraint prevents duplicate alerts
   - Pagination support for large datasets
   - Compound indexes for common filter combinations
   - Connection pooling via asyncpg

API ENDPOINT EXAMPLES
================================================================================

1. CREATE WATCHLIST
POST /api/v1/intel/watchlists
Authorization: Bearer <jwt_token>

Request:
{
  "name": "Downtown Rezoning Monitor",
  "description": "Track rezoning in downtown Vancouver",
  "rules": [
    {"rule_type": "neighborhood", "rule_value": "Downtown"},
    {"rule_type": "signal_type", "rule_value": "rezoning_decision"}
  ]
}

Response:
{
  "id": 1,
  "user_id": 100,
  "name": "Downtown Rezoning Monitor",
  "description": "Track rezoning in downtown Vancouver",
  "is_active": true,
  "rules": [...],
  "created_at": "2024-01-15T10:30:00",
  "updated_at": "2024-01-15T10:30:00"
}

2. LIST ALERTS
GET /api/v1/intel/alerts?unread_only=true&limit=50&offset=0
Authorization: Bearer <jwt_token>

Response: Array of Alert objects

3. MARK ALERT AS READ
POST /api/v1/intel/alerts/1/read
Authorization: Bearer <jwt_token>

Response:
{
  "message": "Alert marked as read"
}

4. GET ALERT COUNTS
GET /api/v1/intel/alerts/count
Authorization: Bearer <jwt_token>

Response:
{
  "total": 10,
  "unread": 3
}
